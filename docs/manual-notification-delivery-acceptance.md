# 通知、提示音、邮件与钉钉手工验收清单（三账号版）

> 适用版本：`8d5787d` 及之后版本  
> 编写日期：2026-07-23  
> 测试范围：站内实时通知、导航红点、页面提示音、SMTP/Resend 邮件、邮件 Outbox、钉钉机器人、工单关闭与归档、项目交付通知。  
> 测试原则：只使用现有 3 个账号完成主流程验收；后台账号通过切换项目角色和分配关系复测不同责任路径。所有业务测试使用专用测试项目，不使用真实客户数据；每个事件使用唯一标题，禁止重复使用同一测试工单判断幂等结果。

## 1. 结果标记

- `[ ]` 未执行
- `[x]` 通过
- `[!]` 失败
- `[-]` 当前环境不适用

每条失败必须记录：

| 字段 | 内容 |
| --- | --- |
| 测试编号 | 例如 `MAIL-03` |
| 操作时间 | 精确到秒，注明时区 |
| 操作账号 | 邮箱、角色 |
| 项目 / 工单 | 项目名称、工单编号 |
| 预期收件人 | 应收到和不应收到的人 |
| 实际结果 | 页面、红点、声音、邮件、钉钉分别记录 |
| 发件箱记录 | 主题、状态、创建时间、发送时间、尝试次数、错误信息 |
| 截图 | 操作页面、发件箱详情、收件箱时间、钉钉消息 |
| 错误编号 | 页面出现“错误编号”时必须完整记录 |

## 2. 时间判定标准

- 即时业务邮件：事件发生后 10 秒内通常应出现在发件箱；实时唤醒失效时，最迟应在 60 秒 Outbox Sweep 内出现。
- 即时业务邮件成功：发件箱在 90 秒内进入“已提交/已发送”类状态；SMTP 收件箱建议最多观察 2 分钟。
- 延迟未读邮件：事件发生后 5 分钟内不得发送；正常接收窗口为第 5～7 分钟。
- 已读取消：在第 5 分钟前阅读后，持续观察到第 7 分钟，仍不得收到对应邮件。
- 发件箱逾期：`sendAfter` 已到期超过 2 分钟仍为“排队中”，判定失败。
- 钉钉业务消息：通常应在 30 秒内到达；超过 60 秒且无明确失败信息，判定失败。
- SMTP 服务商可能存在收件延迟。判断系统是否入队必须以平台发件箱为第一证据，以实际收件时间为第二证据。

## 3. 测试账号与数据

只需要以下 3 个现有账号：

| 代号 | 角色 | 项目关系 | 用途 |
| --- | --- | --- | --- |
| `A` | 平台管理员 | 平台管理员 | 验证管理员收件、平台设置和管理权限 |
| `B` | 后台人员 | 在“项目负责人”和“技术负责人/处理人”之间切换 | 验证未分配兜底、已分配处理人和撤权路径 |
| `C` | 普通客户用户 | 属于测试客户空间 | 创建请求、回复、查看项目交付、确认关闭 |

准备一个标准测试项目 `通知验收项目`：

- 客户空间包含普通客户 `C`。
- 第一阶段将 `B` 设为项目负责人；需要测试已分配路径时，再把 `B` 设为技术负责人/项目成员并分配工单。
- 客户服务请求、进度动态、项目进度、里程碑、项目文件全部开启。
- 准备可上传的 `png`、`pdf` 和不允许扩展名文件各一个。
- `A/B/C` 最好分别使用独立浏览器配置文件；至少保证后台账号和客户账号不在同一个登录会话中互相切换。
- `A/B/C` 先在“账号设置”开启“页面提示音”和“未读邮件提醒”。
- 涉及角色切换时，每次切换后重新登录 `B` 或刷新权限上下文，并在测试记录中注明当时角色。
- 测试标题使用 `MT-日期-编号`，例如 `MT-0723-001`。

## 4. 执行前配置

### PRE-01 生产版本与页面可用

- [ ] **目的**：确认测试环境已运行目标版本。
- **操作**：打开后台、客户中心、服务请求、项目详情、插件中心和设置页。
- **成功**：页面均可打开，无“服务器处理失败”；当前部署对应提交不早于 `8d5787d`。
- **失败**：任一核心页面 500、持续白屏、数据库字段不存在或资源加载失败。发生时停止后续测试。

### PRE-02 邮件真实通道

- [ ] **目的**：确认业务邮件不是写入本地发件箱后停止。
- **操作**：后台设置 → 邮件通道。
- **成功**：当前通道明确显示 `SMTP · 已启用` 或 `Resend · 已启用`；不能同时启用两者。
- **失败**：显示“本地发件箱”、两个通道同时显示启用，或已启用通道缺少必要配置。

### PRE-03 通知规则基线

- [ ] **目的**：建立可重复测试的规则基线。
- **操作**：后台设置 → 通知规则；开启全部“通知红点”和“页面提示音”；开启所有支持的“邮件提醒”；钉钉规则按第 11 节再开启；点击“保存通知规则”。
- **成功**：保存成功；不支持的渠道显示 `—`；邮件开关不能在通知红点关闭时单独开启。
- **失败**：保存后刷新丢失、支持矩阵与页面说明不一致、无需保存就错误生效。

### PRE-04 收件人个人偏好

- [ ] **目的**：避免个人开关干扰基线测试。
- **操作**：`A/B/C` 分别进入账号设置，开启“页面提示音”和“未读邮件提醒”并保存。
- **成功**：刷新页面后开关状态保持；其他登录设备同步相同状态。
- **失败**：刷新恢复旧值、账号之间互相影响。

## 5. 邮件通道与发件箱

### MAIL-01 SMTP 连接检测

- [ ] **目的**：验证 SMTP 主机、端口、加密方式和凭据。
- **前提**：SMTP 配置已保存。
- **操作**：点击“SMTP 连接检测”。
- **成功**：页面提示“SMTP 连接检测通过”；不会向任何邮箱发送邮件。
- **失败**：检测过程发送了邮件；失败信息只有笼统 500，没有可定位原因或错误编号。

### MAIL-02 SMTP 测试邮件

- [ ] **目的**：验证最底层 SMTP 发信能力。
- **操作**：输入 `A` 的邮箱并发送测试邮件。
- **成功**：页面提示已提交；发件箱顶部出现最新记录；`A` 在 2 分钟内收到；发件人邮箱与 SMTP 登录/配置一致，页面只允许修改发件人名称时不得误导为可修改邮箱。
- **失败**：无发件箱记录、记录顺序不按创建时间倒序、状态逾期、收件人或发件人错误。

### MAIL-03 发件箱排序与详情

- [ ] **目的**：验证日志可用于排障。
- **操作**：连续发送 3 封不同主题测试邮件，刷新发件箱，打开每条“查看内容”。
- **成功**：最新创建记录在最上方；时间、收件人、主题、通道、状态、正文和错误信息对应正确。
- **失败**：旧邮件固定置顶、刷新后顺序随机、详情对应到其他邮件。

### MAIL-04 SMTP 与 Resend 互斥

- [ ] **目的**：验证两个通道处于同一层级且只能启用一个。
- **操作**：在已保存两套配置的前提下切换当前通道，再切回 SMTP。
- **成功**：任一时刻只有一个“已启用”；切换不删除另一套已保存配置；新邮件使用切换后的通道。
- **失败**：同时启用、切换丢失密码之外的配置、旧通道继续发送新邮件。

### MAIL-05 本地发件箱保护

- [ ] **目的**：验证关闭真实通道后的明确提示。
- **操作**：仅在测试环境短暂切到本地发件箱，触发一条测试业务事件后恢复 SMTP。
- **成功**：页面明确提示不会对外发送；事件不会悄悄显示为 SMTP 已发送；历史邮件不会因重新开启而自动群发，必须人工确认重试。
- **失败**：重新开启 SMTP 后自动补发所有历史事件、记录消失或状态伪装成功。

### MAIL-06 手动取消与重试

- [ ] **目的**：验证发件箱控制器。
- **前提**：制造或找到一条仍处于“排队中”的测试邮件。
- **操作**：先取消，再点击重试。
- **成功**：取消后状态变“已取消”；重试后生成可追踪的再次投递并使用当前通道；已发送邮件不显示取消操作。
- **失败**：取消后仍发送、同一次重试产生多封、已发送邮件可以重复取消。

### MAIL-07 SMTP 不确定结果

- [ ] **目的**：验证 SMTP 超时不会自动重复发送。
- **操作**：仅在可控测试 SMTP 环境模拟连接中断或超时；恢复后查看记录。
- **成功**：系统提示“SMTP 发送结果不确定”，不自动重试；由测试人员核对收件箱后手动决定是否重试。
- **失败**：系统无限自动重试并造成重复邮件，或完全没有错误上下文。

## 6. 工单收件人与邮件规则

本节先关闭“未读 5 分钟后发送”，按即时模式执行。除特别说明外，收件人不要停留在目标工单详情页。

### REQ-01 客户新建未分配请求

- [ ] **目的**：验证新工单管理员和项目负责人收件链路。
- **前提**：`B` 是项目负责人，工单没有处理人。
- **操作**：`C` 创建 `MT-REQ-001`，暂不分配处理人。
- **成功**：`A/B` 各有一条红点、一次声音和一封邮件；操作者 `C` 不收到自己的通知和邮件。
- **失败**：平台管理员或项目负责人漏收；客户收到自己的提醒；同一收件人重复收到。

### REQ-02 后台代客户新建请求

- [ ] **目的**：验证后台创建时排除操作者本人。
- **操作**：`A` 为测试客户创建 `MT-REQ-002`。
- **成功**：操作者 `A` 不收到自己的通知和邮件；项目负责人 `B` 按规则收到。
- **失败**：`A` 收到自己操作的邮件，或 `B` 漏收。

### REQ-03 分配主处理人

- [ ] **目的**：验证处理人分配邮件。
- **前提**：把 `B` 切换为可处理该项目的技术负责人/项目成员。
- **操作**：`A` 将 `MT-REQ-001` 分配给 `B`。
- **成功**：新处理人 `B` 收到一条分配红点和邮件；操作者 `A` 不收到；客户 `C` 不因后台分配收到标准邮件。
- **失败**：旧处理人或全体人员群收、分配事件没有邮件、重复发送。

### REQ-04 负责人和技术负责人角色切换

- [ ] **目的**：用同一个后台账号验证不同责任关系，不需要额外账号。
- **操作**：先让 `B` 作为项目负责人完成未分配工单测试；再切换为技术负责人并分配工单；最后解除分配并移出项目成员。
- **成功**：作为负责人时接收未分配兜底邮件；作为处理人时接收已分配回复邮件；移出项目且解除分配后不再收到新事件。
- **失败**：角色切换后仍按旧责任关系收件，或移除后继续收到邮件。

### REQ-05 客户回复未分配请求

- [ ] **目的**：验证无处理人时由项目负责人兜底。
- **前提**：`B` 是项目负责人，目标工单未分配。
- **操作**：`C` 在未分配工单公开回复唯一文本。
- **成功**：`A/B` 收到红点和邮件；操作者 `C` 不收到；钉钉规则开启时仅一条钉钉消息。
- **失败**：管理员漏收、项目负责人漏收，或客户收到自己的提醒。

### REQ-06 客户回复已分配请求

- [ ] **目的**：验证当前最关键的管理员与技术负责人双收件链路。
- **前提**：`B` 是技术负责人/处理人，目标工单已分配给 `B`。
- **操作**：由 `C` 公开回复。
- **成功**：`A/B` 各收到一封邮件和红点；操作者 `C` 不收到。
- **失败**：只有处理人收到、只有管理员收到，或客户收到自己的提醒。

### REQ-07 客户操作者排除

- [ ] **目的**：验证普通客户回复不会给自己制造通知。
- **操作**：`C` 连续回复两个不同工单，每条使用唯一文本。
- **成功**：`A/B` 按工单责任关系收到；`C` 不收到自己的站内红点、声音或邮件；邮件中客户名称正确。
- **失败**：客户收到自己的通知，或两条不同工单被错误聚合。

### REQ-08 后台公开回复客户

- [ ] **目的**：验证后台到正式客户的双向提醒。
- **操作**：`B` 关闭“仅内部可见”，公开回复。
- **成功**：客户 `C` 收到红点和邮件；后台操作者 `B` 不收到自己的邮件；`A` 不收到这封面向客户的邮件；邮件链接打开正确工单。
- **失败**：客户漏收、后台操作者收到自己的邮件、链接跳到其他项目或登录后丢失目标。

### REQ-09 内部备注隔离

- [ ] **目的**：验证内部信息绝不外泄。
- **操作**：`B` 开启“仅内部可见”后发送包含唯一关键词的备注。
- **成功**：相关后台人员可见；客户 `C` 的页面、通知、声音和邮件均看不到该关键词；钉钉不发送。
- **失败**：客户任一入口可见、客户收到摘要邮件、钉钉群出现内部内容。

### REQ-10 第一次公开回复与自动接手

- [ ] **目的**：验证自动接手不造成重复通知。
- **操作**：在未分配工单中由有权处理的技术人员首次公开回复。
- **成功**：自动接手和公开回复在页面实时完成；客户只收到一次声音、一条聚合通知和一封邮件。
- **失败**：客户收到“已分配”和“新回复”两封重复邮件或两次声音。

### REQ-11 手动等待客户

- [ ] **目的**：验证客户需要行动的状态邮件。
- **操作**：后台将工单状态改为“等待客户”。
- **成功**：客户 `C` 收到状态通知和邮件；后台操作者不收到自己的邮件。
- **失败**：客户无邮件、自动状态变化也重复产生相同状态邮件。

### REQ-12 手动已解决

- [ ] **目的**：验证解决通知和客户确认入口。
- **操作**：后台将工单标记“已解决”。
- **成功**：客户 `C` 收到已解决邮件；客户回复区出现遮罩，包含“继续反馈”和“确认关闭”；移动端按钮可操作。
- **失败**：客户仍直接看到普通输入框、遮罩溢出、客户没有状态邮件。

### REQ-13 客户继续反馈

- [ ] **目的**：验证已解决后重新开启。
- **操作**：客户 `C` 点击“继续反馈”并发送内容。
- **成功**：状态恢复“处理中”；后台 `A/B` 按客户回复规则收到通知；不会发送“已关闭”邮件。
- **失败**：仍保持已解决、回复丢失、旧的 7 天关闭计时继续生效。

### REQ-14 客户确认关闭

- [ ] **目的**：验证关闭权限只属于客户确认流程。
- **操作**：重新标记已解决，由客户 `C` 点击“确认关闭”。
- **成功**：状态变“已关闭”；客户不能继续回复；客户本人不收到自己确认关闭的标准邮件；后台不能绕过流程直接关闭。
- **失败**：后台可直接关闭、客户确认后仍可回复、客户收到自己的关闭邮件。

### REQ-15 自动状态变化去重

- [ ] **目的**：验证公开回复引发的自动状态变化不重复发信。
- **操作**：在“等待客户”状态由客户公开回复。
- **成功**：状态自动回到“处理中”；后台只收到客户回复通知，不额外收到“状态变更”邮件和红点。
- **失败**：同一次回复产生回复邮件加状态邮件两套提醒。

### REQ-16 公开独立附件

- [ ] **目的**：验证独立附件只产生站内通知。
- **操作**：上传一个脱离消息的公开附件。
- **成功**：相关用户收到附件红点；通知规则中该场景邮件显示不支持；客户权限允许时可下载。
- **失败**：错误发送邮件、附件红点归到错误工单、无权限用户可下载。

### REQ-17 回复内图片与附件

- [ ] **目的**：验证富文本图片不产生额外独立附件通知。
- **操作**：发送一条含内嵌图片和待发送附件的公开回复。
- **成功**：只按“公开回复”产生一次聚合通知和邮件；正文和图片在详情中正常展示。
- **失败**：同一次回复再产生独立附件邮件、多条红点或损坏正文格式。

### REQ-18 归档与恢复

- [ ] **目的**：区分“关闭”和“归档”。
- **前提**：工单已解决或已关闭。
- **操作**：后台归档，再从“已归档”恢复。
- **成功**：归档后从“全部”和状态列表隐藏，只在“已归档”显示；客户只能查看不能归档；恢复后回到对应状态列表；归档/恢复不发邮件。
- **失败**：归档等同关闭、客户可以操作归档、归档仍出现在“全部”、产生业务邮件。

## 7. 未读 5 分钟、聚合与取消

本节开启“未读 5 分钟后发送”。每次测试使用新工单，避免旧通知聚合影响时间。

### DELAY-01 未读到期发送

- [ ] **目的**：验证开关只改变发送时机。
- **操作**：客户触发一条公开回复，收件人 7 分钟内不打开通知和工单。
- **成功**：前 5 分钟无邮件；第 5～7 分钟收到；通知红点从事件发生时立即出现。
- **失败**：邮件立即发送、红点也延迟 5 分钟、超过 7 分钟无发件箱记录。

### DELAY-02 阅读取消

- [ ] **目的**：验证阅读会取消尚未到期邮件。
- **操作**：事件发生 1～2 分钟后，收件人进入对应工单。
- **成功**：红点立即消失；观察到第 7 分钟仍不收邮件；待发记录不会最终发送。
- **失败**：已阅读仍发信、必须刷新页面才取消。

### DELAY-03 聚合后重新计时

- [ ] **目的**：验证连续消息按最后一次有效事件聚合。
- **操作**：第 0 分钟和第 3 分钟分别发送两条客户回复，收件人不阅读。
- **成功**：不会在第 5 分钟发送旧版本；应从第 3 分钟重新计算，在约第 8～10 分钟发送聚合后的最新邮件。
- **失败**：两条消息各发一封、旧版本先发、计数和摘要遗漏最新消息。

### DELAY-04 阅读后出现新事件

- [ ] **目的**：验证阅读只取消旧事件，不永久关闭后续邮件。
- **操作**：阅读并取消第一条待发邮件，再触发第二条新回复且不阅读。
- **成功**：第一条不发，第二条重新进入新的 5 分钟周期并正常发送。
- **失败**：阅读一次后该工单永远不再发邮件，或旧事件被重新补发。

### DELAY-05 关闭个人邮件偏好

- [ ] **目的**：验证个人开关只影响本人。
- **前提**：目标工单已分配给 `B`，由客户 `C` 触发回复，因此 `A/B` 都是预期收件人。
- **操作**：事件发生后，在到期前让 `B` 关闭“未读邮件提醒”；`A` 保持开启。
- **成功**：`B` 的待发邮件永久取消，`A` 正常收到；两人的站内通知不受影响。
- **失败**：关闭一个账号导致全局停发，或 `B` 仍收到已排期邮件。

### DELAY-06 关闭业务邮件规则

- [ ] **目的**：验证规则关闭会取消对应待发邮件且不补发历史。
- **操作**：触发待发邮件后，在到期前关闭该场景“邮件提醒”；等待到第 7 分钟，再重新开启。
- **成功**：旧事件不发送；重新开启只对之后的新事件生效。
- **失败**：重新开启后群发历史通知、旧待发邮件继续发送。

### DELAY-07 关闭客户模块或撤销权限

- [ ] **目的**：验证发送前再次检查权限。
- **操作**：触发项目交付待发邮件后，在到期前关闭对应客户模块，或将测试客户移出客户空间。
- **成功**：已有对应未读被清理或失效；邮件不发送；重新开启模块不补发历史。
- **失败**：失去权限后仍收到内容或链接仍可访问。

## 8. Presence、实时刷新、声音与红点

### RT-01 跨页面提示音

- [ ] **目的**：验证声音覆盖登录后的所有主站页面。
- **操作**：让收件人停留在设置页或项目列表，由另一账号触发新工单/回复。
- **成功**：无需位于工单页也能听到一次提示音，红点实时出现。
- **失败**：只有刷新或进入工单页才响、同一事件连续响多次。

### RT-02 操作者本人静音

- [ ] **目的**：验证本地操作不产生回声声音。
- **操作**：操作者自己发布回复、阶段或动态。
- **成功**：其他目标用户按规则响；操作者本人不响、不出现自己的红点。
- **失败**：自己操作自己响、自己收到通知。

### RT-03 账号级静音

- [ ] **目的**：验证“页面提示音”即时生效。
- **操作**：关闭后台账号 `B` 的页面提示音并保存，不刷新页面，随后由客户 `C` 触发事件。
- **成功**：`B` 不响，但红点和邮件按独立开关正常；重新开启后新事件恢复声音。
- **失败**：必须刷新才生效、静音同时关闭邮件或红点。

### RT-04 当前工单 Presence 抑制

- [ ] **目的**：验证正在阅读时不制造未读和邮件。
- **操作**：后台账号 `B` 打开目标工单并保持页面活动，客户 `C` 从另一窗口回复。
- **成功**：`B` 可听到声音并实时看到消息，但不增加该工单红点、不排期邮件；`A` 仍正常收到。
- **失败**：当前查看者仍收到未读邮件，或 Presence 把所有收件人一起抑制。

### RT-05 多标签页 Presence

- [ ] **目的**：验证一个标签页离开不应覆盖另一个活跃标签页。
- **操作**：`B` 用两个标签页打开同一工单，关闭其中一个后由 `C` 触发客户回复。
- **成功**：另一个活跃标签仍保持 Presence；不产生 `B` 的未读邮件。
- **失败**：关闭一个标签后立即被判离线，或者两个标签产生重复声音。

### RT-06 Presence 过期

- [ ] **目的**：验证关闭页面后不会永久抑制通知。
- **操作**：关闭所有目标工单标签，等待 Presence 过期后再触发回复。
- **成功**：过期后恢复正常红点和邮件；不会永久处于“正在查看”。
- **失败**：长时间不再收到该工单通知。

### RT-07 输入状态

- [ ] **目的**：验证输入提示不进入通知中心。
- **操作**：客户和后台分别输入、清空、离开输入框。
- **成功**：对方实时看到输入提示；不播放业务声音、不创建红点、不发邮件。
- **失败**：输入状态成为永久通知、离开后提示不消失。

### RT-08 红点即时清除

- [ ] **目的**：验证进入详情后无需刷新。
- **操作**：从服务请求列表进入有未读的工单，再返回列表并观察顶部铃铛和左侧导航。
- **成功**：工单、列表、导航和铃铛数字同步减少；无需刷新。
- **失败**：局部消失但顶部仍保留，必须刷新才一致。

### RT-09 超过 30 条通知

- [ ] **目的**：验证铃铛数字不受首屏 30 条限制。
- **操作**：使用批量测试数据产生至少 35 条未读，打开通知菜单并加载更早通知。
- **成功**：铃铛、导航、项目和工单计数显示完整总数；每次加载 30 条；游标分页无重复、无遗漏。
- **失败**：总数停在 30、加载更早后重复、红点数量与列表不一致。

### RT-10 浏览器后台标题提醒

- [ ] **目的**：验证失焦标签页提醒和恢复。
- **操作**：将站点标签页切到后台后触发事件，再切回。
- **成功**：后台标签标题出现注意提示；返回后恢复原始标题。
- **失败**：标题永久闪烁、多个页面标题互相覆盖。

## 9. 项目交付通知

本节要求对应客户模块和通知规则均开启；所有事件均使用客户可见内容。

### PROJ-01 发布进度动态

- [ ] **目的**：验证项目动态红点、声音和邮件。
- **操作**：后台发布新动态 `MT-PROJ-001`。
- **成功**：客户 `C` 收到通知和邮件；后台操作者被排除；进入“进度动态”只清除动态类未读。
- **失败**：客户漏收、后台自己收到、动态模块未开启仍发给客户。

### PROJ-02 修改已有动态

- [ ] **目的**：验证修正文案不制造新提醒。
- **操作**：编辑 `MT-PROJ-001` 的文字，不新建动态。
- **成功**：内容更新，但不新增红点、声音和邮件。
- **失败**：每次编辑都重新通知客户。

### PROJ-03 动态评论

- [ ] **目的**：验证新评论与编辑评论的差异。
- **操作**：新增客户可见评论，再修改该评论。
- **成功**：新增评论产生一次通知；编辑不产生新的未读邮件；内部评论不通知客户。
- **失败**：内部评论外泄、编辑重复通知。

### PROJ-04 阶段变化

- [ ] **目的**：验证阶段规则及项目进度模块权限。
- **操作**：切换项目当前阶段。
- **成功**：客户项目方格、项目标签和通知中心出现对应红点；邮件按“项目阶段变化”规则发送。
- **失败**：只刷新页面没有红点、客户进度模块关闭后仍发送。

### PROJ-05 里程碑新增、修改、删除

- [ ] **目的**：验证三种里程碑事件和统一样式。
- **操作**：依次新增、修改、删除不同里程碑。
- **成功**：每个动作各产生一次对应通知；客户和后台展示结构一致但权限按钮不同；未设置日期时不显示“未设置”。
- **失败**：后台可见标签与客户模块标准不一致、无法编辑删除、一次操作产生多条通知。

### PROJ-06 项目文件上传

- [ ] **目的**：验证公开文件通知。
- **操作**：上传一个非编辑器内嵌的公开文件。
- **成功**：客户收到 `PROJECT_FILE` 红点和邮件；进入文件标签只清除文件未读。
- **失败**：文件被归入动态通知、客户文件模块关闭后仍可见或仍发信。

### PROJ-07 富文本内嵌图片排除

- [ ] **目的**：验证内嵌图片不会被当作项目文件再次通知。
- **操作**：发布含图片的富文本动态或里程碑说明。
- **成功**：只产生所属动态/里程碑通知；不额外产生项目文件红点和邮件。
- **失败**：一张图片产生两类邮件或文件标签出现不应展示的内嵌资源。

### PROJ-08 模块红点独立清除

- [ ] **目的**：验证动态、里程碑、文件和工单互不误清。
- **操作**：同时制造四类未读，依次进入各标签。
- **成功**：每次只清除当前模块；工单未读仍归“服务请求”。
- **失败**：打开任意一个标签就清空整个项目所有未读。

### PROJ-09 模块关闭清理

- [ ] **目的**：验证隐藏客户模块时清理旧未读。
- **操作**：先制造未读，再由后台关闭对应客户模块。
- **成功**：客户标签隐藏，已有对应未读和待发邮件被清除；后台仍可正常管理；重新开启不补发历史。
- **失败**：隐藏标签后铃铛仍残留不可访问通知、后台标签也被错误隐藏。

## 10. 归档、权限与隔离

### ACL-01 客户模块关闭

- [ ] **目的**：验证客户限制不影响后台工作。
- **操作**：关闭客户服务请求模块。
- **成功**：客户看不到/不能访问服务请求；客户旧未读清理；后台人员仍可访问和处理。
- **失败**：后台也被禁用、客户通过旧链接仍可进入。

### ACL-02 后台人员移出项目后的隔离

- [ ] **目的**：用现有 `B` 验证项目和工单不是面向所有后台人员广播。
- **操作**：先解除 `B` 的工单分配，再将 `B` 移出测试项目，随后由 `C` 创建并回复一个新工单。
- **成功**：`B` 不再收到该项目事件、工单红点、声音和邮件，也不能继续以项目成员身份处理目标资源；`A` 仍正常收到管理员提醒。
- **失败**：`B` 只因是后台账号就继续收到项目内容，或旧权限长期残留。

### ACL-03 单客户账号可验证边界

- [-] **说明**：当前只有一个普通客户账号，无法通过手工操作证明“两个客户空间之间完全隔离”。
- **当前可测**：关闭客户模块、撤销客户项目权限后，使用 `C` 的旧项目、工单和附件链接访问。
- **成功**：旧链接返回无权限或不存在，通知摘要不再包含目标资源。
- **补充依据**：跨客户空间 RLS 隔离继续以集成测试为准；未来有第二个客户账号时再执行真正的交叉访问测试。

### ACL-04 处理人权限撤销

- [ ] **目的**：验证撤销后不再接收待发邮件。
- **操作**：触发 `B` 的延迟邮件后，在到期前解除其处理人并移除项目成员关系。
- **成功**：待发邮件取消，后续不再收到该工单事件，旧链接无法继续处理。
- **失败**：撤权后仍收到邮件或可操作工单。

## 11. 钉钉机器人

### DING-01 未启用时条件渲染

- [ ] **目的**：验证未启用插件时不展示无效控制器。
- **操作**：停用钉钉插件并进入通知规则。
- **成功**：整个“钉钉机器人”列隐藏；已保存规则不影响邮件和红点。
- **失败**：未启用仍显示钉钉列或大量不可用开关。

### DING-02 Webhook 校验与保密

- [ ] **目的**：验证只接受官方 Webhook 且不回显密钥。
- **操作**：依次尝试空地址、HTTP 地址、伪造域名、缺少 `access_token`、合法官方 HTTPS 地址。
- **成功**：前四种明确拒绝；合法地址保存；重新打开设置不回显完整 Webhook/令牌。
- **失败**：接受伪造域名、错误中暴露令牌、普通配置接口返回完整 Webhook。

### DING-03 启用与环境检测不发消息

- [ ] **目的**：验证管理操作不骚扰群聊。
- **操作**：保存配置、启用插件、点击“运行环境检测”。
- **成功**：状态变“环境正常”，上述操作均不发送钉钉消息。
- **失败**：启用或每次检测都发送“绑定成功”等消息。

### DING-04 测试发送

- [ ] **目的**：验证显式测试入口。
- **操作**：点击“测试发送”。
- **成功**：页面明确提示成功；钉钉群在 60 秒内收到一条带“工单通知”关键词的测试消息。
- **失败**：无消息、重复消息、失败只显示笼统错误。

### DING-05 模板编辑与预览

- [ ] **目的**：验证模板变量、预览和保存。
- **操作**：编辑“新建服务请求”模板，插入多个受支持变量，保存并刷新。
- **成功**：预览正确；刷新后保持；未知变量被拒绝；Webhook 健康状态不因只改模板而失效。
- **失败**：出现未替换变量、保存模板导致要求重新填写 Webhook。

### DING-06 模板测试快照

- [ ] **目的**：验证测试消息使用当前编辑内容。
- **操作**：不污染真实业务数据，使用模板弹窗中的测试发送。
- **成功**：群消息与预览内容一致；只发送一次。
- **失败**：使用旧模板、变量内容错位或重复发送。

### DING-07 新建请求业务消息

- [ ] **目的**：验证 `REQUEST_CREATED` 规则。
- **操作**：开启对应钉钉规则后，由客户新建请求。
- **成功**：群里收到一条新工单消息；邮件是否发送由邮件规则独立决定。
- **失败**：规则关闭仍发送、同一工单重复入群。

### DING-08 客户公开回复业务消息

- [ ] **目的**：验证钉钉只提醒客户方向回复。
- **操作**：客户公开回复、客户内部不可见场景不适用、后台再公开回复一次。
- **成功**：客户公开回复发送一条；后台回复客户不发送；内部备注不发送。
- **失败**：后台每次回复也刷群、内部内容进入钉钉。

### DING-09 邮件与钉钉独立组合

- [ ] **目的**：验证后台人员可灵活选择通道。
- **操作**：依次测试“仅邮件”“仅钉钉”“邮件+钉钉”“两者关闭”四种规则组合，每次保存后触发新事件。
- **成功**：实际投递与组合完全一致；钉钉不受邮件 5 分钟延迟影响；一个通道失败不阻塞另一个。
- **失败**：必须同时开启、邮件失败导致钉钉不发、关闭后仍发送历史消息。

### DING-10 停用与待处理消息

- [ ] **目的**：验证停用插件后不会继续发送旧队列。
- **操作**：在可控测试环境制造待处理钉钉消息后停用插件。
- **成功**：待处理消息进入跳过/取消终态，不会在重新启用后补发历史。
- **失败**：停用后仍发、重新启用后群发旧消息。

## 12. 7 天自动关闭

生产环境不得直接修改数据库时间。该组采用长期观察；如需加速，只能在隔离测试数据库执行。

### CLOSE-01 未满 7 天不关闭

- [ ] **目的**：验证不会提前关闭。
- **操作**：记录已解决准确时间，在第 1～6 天每天检查。
- **成功**：状态始终保持已解决。
- **失败**：未满 7×24 小时提前关闭。

### CLOSE-02 满 7 天自动关闭

- [ ] **目的**：验证定时 Worker。
- **操作**：超过解决时间 7 天后，等待下一次每小时第 7 分钟扫描。
- **成功**：状态自动变已关闭；出现一条系统消息说明 7 天未反馈；不产生重复系统消息；正式客户不收到重复状态业务邮件。
- **失败**：未关闭、每小时重复写消息、一个失败工单阻塞其他到期工单。

### CLOSE-03 继续反馈取消旧周期

- [ ] **目的**：验证重新开启后旧解决时间不再生效。
- **操作**：已解决后在第 7 天前继续反馈，再观察原到期时间。
- **成功**：恢复处理中，原到期点不会自动关闭；之后再次标记解决时从新时间重新计算。
- **失败**：继续反馈后仍按旧时间关闭。

## 13. 邀请与账号邮件 Outbox

### ACCOUNT-00 团队成员登录邮箱变更

- [ ] **目的**：验证团队成员本人和平台管理员都有正确入口。
- **本人操作**：使用 `B` 进入“个人设置” → “登录邮箱”，输入一个可接收验证邮件的新邮箱并发送。
- **管理员操作**：使用 `A` 进入“团队” → 编辑 `B` → “修改邮箱”，为 `B` 发起另一条邮箱变更。
- **成功**：两条路径都必须向新邮箱发送 24 小时有效确认链接；新邮箱确认前旧邮箱仍可登录；新申请会取消旧申请；确认后邮箱更新且该账号其他会话退出；新邮箱收到完成通知，原邮箱收到安全提醒。
- **失败**：成员个人设置只能看不能改、管理员按钮缺失、直接覆盖邮箱而不验证、确认后旧会话仍有效、客户原有邮箱修改入口被破坏。

### ACCOUNT-01 客户成员邀请

- [-] **说明**：该项需要一个尚未注册的收件邮箱，不要求创建第四个平台账号；没有备用邮箱时可跳过。
- **目的**：验证邀请记录和邮件 Outbox 同事务创建。
- **操作**：客户 Owner 邀请一个可接收邮件但尚未注册的测试邮箱。
- **成功**：邀请创建成功时发件箱一定有对应邮件；队列临时失败时邀请仍可追踪且邮件保持可重试，不出现“邀请存在但无邮件记录”。
- **失败**：页面说邀请成功但发件箱无记录、重复点击创建多份不可控邀请。

### ACCOUNT-02 密码重置

- [ ] **目的**：验证账号即时邮件与业务规则互不干扰。
- **操作**：对测试账号发起密码重置。
- **成功**：即使业务邮件规则关闭，密码重置仍进入真实邮件通道；链接只能按预期使用。
- **失败**：业务邮件开关误关账号邮件、无 Outbox 记录。

### ACCOUNT-03 邮箱变更验证

- [-] **说明**：该项需要一个可接收验证邮件的备用邮箱；没有备用邮箱时可跳过，禁止拿唯一管理员邮箱冒险。
- **目的**：验证排队失败不回滚邮箱变更流程。
- **操作**：发起测试客户邮箱变更，观察验证邮件状态和重试入口。
- **成功**：邮件失败时显示待发送/失败并允许重试；验证成功后邮箱更新；完成通知失败不回滚已完成修改。
- **失败**：邮件暂时失败导致变更记录消失、已完成邮箱被回滚。
